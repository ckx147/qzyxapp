## 核心结论

- 玩法和儿童向包装已经比较完整。
- 状态全在前端，本地 `localStorage` 保存。
- 排行榜是本地模拟，不是云端数据。
- 小程序上线前需要处理身份、云存储、排行榜和合规。
- 积分重复发放、模板残留和构建大 chunk 警告均已处理并验证。
- 当前最大产品架构风险是小程序路线待用户确认和数据仍在本地。
- 路线矩阵当前建议优先评估 Taro/uni-app MVP。

## 最大风险

### 已验证：积分重复发放已修复

游戏结算曾重复加分，影响积分、排行榜、商店经济、成就反馈；现已统一通过 `App.tsx` 的 `handlePointsChange` 结算。

当前规则：

- 只有 `App.tsx` 的 `handlePointsChange` 可以改 `profile.points`。
- 子游戏组件只更新游戏记录和成就，不直接改积分。

### P1：不能直接当小程序跑

不可直接迁移的 Web API：

- `localStorage`
- `window`
- `document`
- `new Image`
- `AudioContext`
- React DOM

## 下一步建议

1. 用户确认小程序路线，当前建议 Taro/uni-app MVP。
2. 基于 `微信云开发落地清单.md` 拆云开发任务。
3. 做四个游戏逐项通关交互测试。
4. 评估本地假排行榜和云端同步方案。
