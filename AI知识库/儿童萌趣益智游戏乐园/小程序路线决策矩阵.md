# 儿童萌趣益智游戏乐园 - 小程序路线决策矩阵

标签：#小程序路线 #决策矩阵 #架构决策

## 决策目标

当前项目是 Vite + React + TypeScript Web 原型，不是微信小程序工程。这个矩阵用于决定下一阶段是快速封装、跨端迁移，还是原生重写。

评分说明：

- 5 分：非常适合当前目标。
- 3 分：可接受，但有明显代价。
- 1 分：不适合，或后续风险较高。

## 路线对比

## 结论

当前更推荐路线 B：Taro/uni-app 迁移。

理由：

- 目标是儿童微信小程序，不能长期停留在纯 Web 原型。
- 当前 React/TypeScript 逻辑有一定复用价值，直接原生重写成本较高。
- Taro/uni-app 能更自然接入微信登录、云开发、授权、分享和页面生命周期。
- 相比 WebView，正式上线、儿童隐私、云端数据和审核确定性更稳。

## 分阶段策略

### 阶段 1：继续保留 Web 原型

目的：

- 做玩法验证和 UI 调整。
- 完成四个游戏逐项交互测试。
- 保留当前自动化验证作为回归基线。

退出条件：

- 四个游戏主要路径可稳定玩。
- 积分、打卡、商店、成就、排行榜逻辑没有明显重复结算。
- 小程序路线已确认。

### 阶段 2：Taro/uni-app MVP

目的：

- 搭建小程序工程骨架。
- 迁移首页、积分、打卡、商店、成就、个人档案。
- 将 `localStorage` 状态迁移到本地小程序存储或云端接口。
- 优先迁移一个小游戏作为技术样板。

退出条件：

- 微信开发者工具可运行。
- 登录、用户档案、积分流水、每日打卡能走通。
- 一个小游戏从开始到结算可用。

### 阶段 3：正式小程序化

目的：

- 迁移剩余游戏。
- 接入云端排行榜、成就状态、家长授权和数据删除流程。
- 做真机触控、音效、性能和审核前检查。

## 什么时候选择 WebView

如果目标只是快速内测或给家长/团队看玩法，可以选择 WebView。

不建议把 WebView 当长期正式路线，因为：

- 微信原生能力受限。
- 儿童隐私、家长授权和数据删除流程更难做得清晰。
- 排行榜、登录、分享和云端数据会绕路。

## 什么时候选择原生重写

如果目标是长期正式儿童产品，且愿意承受更高初期成本，可以选择原生重写。

适合条件：

- 不急着上线。
- 更重视微信生态稳定性和审核确定性。
- 希望未来减少跨端框架约束。
- 愿意重新实现 UI、动画、状态和游戏交互。

## 下一步建议

1. 用户确认路线：推荐先选 Taro/uni-app MVP。
2. 创建小程序迁移任务清单。
3. 把 `数据模型草案.md` 转成 `微信云开发落地清单.md` 中的集合、权限和云函数。
4. 先迁移非游戏主流程，再挑一个小游戏做样板。
