## DR-001：知识库作为新窗口交接入口

日期：2026-06-08

决策：

- 使用 `D:\儿童微信小程序开发\AI知识库` 作为 Obsidian 知识库。
- 新窗口先读知识库短文档，再按任务读取源码。

原因：

- 项目较大，减少新窗口 token 消耗和重复分析时间。

## DR-002：低 token 读取优先级

日期：2026-06-09

决策：

- 新窗口默认只读 `README.md`、`新窗口提示词.md`、`当前状态.md`。
- 其他文件按任务需要读取。
- 不默认全量扫描 `src/components`。

原因：

- 避免上下文被长组件占满。

## DR-003：积分系统统一入口

日期：2026-06-09

状态：已落实并验证

决策：

- 积分只能通过 `src/App.tsx` 中的 `handlePointsChange` 修改。
- 子组件不直接修改 `profile.points`。

原因：

- 当前多个小游戏存在重复发放积分的问题。
- 统一入口便于排行榜同步、通知、音效和后续云端积分流水。

## DR-004：小程序路线暂未定

日期：2026-06-09

状态：待用户确认

备选：

- 保留 React Web，微信小程序用 WebView 承载。

- 重写为原生微信小程序。

当前建议：

- 如果决定长期正式儿童产品且能接受更高成本，可以选择原生重写。

## DR-005：云端数据模型先按审计友好设计

日期：2026-06-09

状态：草案已建立

决策：

- 积分采用余额 + 流水模型，不只存一个总积分。
- 每日打卡一人一天一条，避免只存 streak。
- 成就状态按用户和成就 id 独立记录。
- 排行榜从 `user_stats.pointsBalance` 或快照产生，不直接信任客户端排行。

原因：

- 当前项目已有积分、商店、打卡、成就和排行榜，后续云端化需要可追溯。
- 儿童产品应减少敏感信息采集，保留最小必要数据。

参考：

- `数据模型草案.md`

## DR-006：微信云开发按 MVP 集合先落地

日期：2026-06-09

状态：草案已建立

决策：

- MVP 先考虑 `users`、`user_stats`、`point_transactions`、`achievements`、`checkins`、`inventory_items`。
- `game_records`、`leaderboard_snapshots`、`inventory_transactions` 可按上线策略后置。
- 所有积分变化必须走云函数和积分流水，客户端不直接决定余额。

原因：

- 当前项目已有积分、商店、打卡、成就和排行榜，云端化必须先保证可追溯和防重复。
- 先做 MVP 集合可以降低迁移复杂度，同时保留后续审计能力。

参考：

- `微信云开发落地清单.md`
