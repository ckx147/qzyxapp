# 儿童萌趣益智游戏乐园 - 数据模型草案

标签：#数据模型 #微信云开发 #云端同步 #儿童小程序

## 设计目标

这份草案用于从当前本地 `localStorage` 原型，过渡到微信小程序或云端同步版本。它不绑定具体实现，可以映射到微信云开发数据库、自有后端数据库，或 Taro/uni-app 后端服务。

核心目标：

- 支持微信登录后的跨设备数据同步。
- 让积分、成就、打卡、排行榜可追溯。
- 避免只存一个总积分导致无法审计。
- 为儿童产品保留最小必要数据，减少隐私风险。

## 关键原则

- 积分必须有流水，不只存余额。
- 排行榜从聚合数据产生，不允许直接信任客户端上报排行。
- 游戏记录可以客户端提交，但服务端需要做基本校验和限频。
- 儿童身份信息尽量弱化，不存真实姓名、手机号、头像原图等敏感信息。
- 家长授权、隐私政策和数据删除机制需要在正式上线前补齐。

## 集合概览

| 集合 | 用途 | 当前本地来源 |
| --- | --- | --- |
| `users` | 用户基础档案 | `UserProfile` |
| `user_stats` | 用户聚合统计 | `profile.records`、`points`、`feedHappiness` |
| `point_transactions` | 积分流水 | `handlePointsChange` |
| `game_records` | 单局游戏记录 | 四个游戏组件 |
| `achievements` | 用户成就状态 | `Achievement[]` |
| `checkins` | 每日打卡记录 | `CheckInState` |
| `inventory_items` | 背包食物数量 | `profile.inventory` |
| `leaderboard_snapshots` | 排行榜快照或缓存 | `INITIAL_LEADERBOARD` |

## users

用户基础档案。建议一名微信用户对应一条主档案，后续如要支持多儿童档案，可再扩展 `child_profiles`。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 云数据库主键 |
| `openid` | string | 微信 openid，仅服务端可信 |
| `nickname` | string | 昵称，默认“聪明小探险家” |
| `avatarId` | string | 预设头像 id 或云文件 id |
| `createdAt` | date | 创建时间 |
| `updatedAt` | date | 更新时间 |
| `lastLoginAt` | date | 最近登录时间 |
| `status` | string | `active` / `disabled` / `deleted` |

索引建议：

- `openid` 唯一索引
- `updatedAt`

隐私注意：

- 不建议存真实姓名、手机号。
- 自定义头像如果包含真人照片，正式上线前需要家长授权和删除能力。

## user_stats

用户当前聚合状态，供首页、个人页、排行榜快速读取。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `userId` | string | 关联 `users._id` |
| `pointsBalance` | number | 当前积分余额 |
| `feedHappiness` | number | 小布好感度，0-100 |
| `records` | object | 当前最佳/累计游戏记录 |
| `checkInStreak` | number | 当前连续打卡天数 |
| `lastCheckInDate` | string | YYYY-MM-DD，建议按 Asia/Shanghai |
| `updatedAt` | date | 更新时间 |

`records` 建议结构：

```json
{
  "bombGuesses": 0,
  "bombExplodes": 0,
  "bombClears": 0,
  "klotskiBestMoves3x3": 9999,
  "klotskiBestTime3x3": 9999,
  "klotskiBestMoves4x4": 9999,
  "klotskiBestTime4x4": 9999,
  "schulteBest3x3": 9999,
  "schulteBest4x4": 9999,
  "schulteBest5x5": 9999,
  "gomokuWins": 0,
  "gomokuLosses": 0,
  "gomokuDraws": 0
}
```

索引建议：

- `userId` 唯一索引
- `pointsBalance` 降序，用于排行榜

## point_transactions

积分流水。后续所有加减积分都应该写入这里，再更新 `user_stats.pointsBalance`。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `userId` | string | 用户 id |
| `amount` | number | 正数加分，负数扣分 |
| `balanceAfter` | number | 本次变更后的余额 |
| `reason` | string | 原因文案 |
| `sourceType` | string | 来源类型 |
| `sourceId` | string | 关联记录 id，可为空 |
| `createdAt` | date | 创建时间 |
| `clientRequestId` | string | 幂等 id，防重复提交 |

`sourceType` 建议枚举：

- `daily_checkin`
- `shop_purchase`
- `game_bomb`
- `game_klotski`
- `game_schulte`
- `game_gomoku`
- `achievement_reward`
- `admin_adjustment`

校验建议：

- 同一个 `clientRequestId` 只能成功一次。
- 扣分后余额不能低于 0。
- 服务端根据规则计算 `amount`，不要完全信任客户端传值。

## game_records

单局游戏记录。用于复盘、统计和服务端反作弊基础校验。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `userId` | string | 用户 id |
| `gameType` | string | `bomb` / `klotski` / `schulte` / `gomoku` |
| `mode` | string | 难度或模式 |
| `result` | string | `win` / `loss` / `draw` / `completed` |
| `scoreDelta` | number | 本局积分变化 |
| `durationSec` | number | 用时 |
| `moves` | number | 步数，部分游戏可为空 |
| `details` | object | 游戏专属详情 |
| `createdAt` | date | 创建时间 |
| `clientRequestId` | string | 幂等 id |

`details` 示例：

```json
{
  "gridSize": 3,
  "challengeMode": "normal",
  "bestRecordUpdated": true
}
```

## achievements

用户成就状态。当前每个成就有 7 个阶段，建议一条记录对应一个用户的一个成就。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `userId` | string | 用户 id |
| `achievementId` | string | 如 `ach_checkin_1` |
| `tier` | number | 1-7 |
| `targetValue` | number | 当前阶段目标 |
| `progress` | number | 当前进度 |
| `unlocked` | boolean | 当前阶段是否达成 |
| `unlockedAt` | date | 达成时间 |
| `rewardsClaimed` | boolean | 当前阶段奖励是否领取 |
| `updatedAt` | date | 更新时间 |

索引建议：

- `userId + achievementId` 唯一索引

规则建议：

- 成就配置本身不要存在用户记录里，放服务端常量或配置表。
- 用户记录只存状态和进度。

## checkins

每日打卡记录。建议一人一天一条，避免只存 streak 造成无法追溯。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `userId` | string | 用户 id |
| `date` | string | YYYY-MM-DD，按 Asia/Shanghai |
| `streakAfter` | number | 打卡后连续天数 |
| `rewardPoints` | number | 奖励积分 |
| `rewardItemName` | string | 奖励食物名 |
| `rewardItemCount` | number | 奖励数量 |
| `createdAt` | date | 创建时间 |

索引建议：

- `userId + date` 唯一索引

## inventory_items

背包食物数量。

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `userId` | string | 用户 id |
| `itemName` | string | 如 `糖果`、`苹果` |
| `count` | number | 当前数量 |
| `updatedAt` | date | 更新时间 |

索引建议：

- `userId + itemName` 唯一索引

可选增强：

- 如果未来要审计食物来源，可增加 `inventory_transactions`。
- 当前阶段可以先只用当前数量，积分流水已经能覆盖购买行为。

## leaderboard_snapshots

排行榜可以实时从 `user_stats.pointsBalance` 查询，也可以定时生成快照。

实时查询适合早期：

- 按 `pointsBalance` 降序取前 N 名。
- 返回 `nickname`、`avatarId`、`pointsBalance`。

快照字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 主键 |
| `scope` | string | `global` / `friends` / `classroom` |
| `period` | string | `all_time` / `daily` / `weekly` |
| `items` | array | 排行榜条目 |
| `generatedAt` | date | 生成时间 |

注意：

- 排行榜不要存真实身份。
- 儿童产品建议默认展示昵称和卡通头像。

| `profile.id` | `users._id` |

## 最小 MVP 数据方案

如果先做 MVP，不必一次上全量模型。建议最小集合：

1. `users`
2. `user_stats`
3. `point_transactions`
4. `achievements`
5. `checkins`

可以暂缓：

- `game_records`：如果先只同步最佳记录，可以稍后加。
- `leaderboard_snapshots`：早期可直接查 `user_stats`。
- `inventory_transactions`：早期只存 `inventory_items` 当前数量。

| `claimAchievementReward` | 领取成就奖励 |
| `getLeaderboard` | 获取排行榜 |
