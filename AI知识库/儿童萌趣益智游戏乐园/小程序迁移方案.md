# 儿童萌趣益智游戏乐园 - 小程序迁移方案

标签：#微信小程序 #迁移方案 #架构决策

## 当前前提

当前 APP 是 Vite + React Web 原型，不是微信小程序工程。项目内使用了多种浏览器 API，不能直接运行在小程序原生环境。

## 三条路线

### 路线 A：WebView 承载 React Web

做法：

- 保留当前 React/Vite APP。
- 部署成 H5 页面。
- 微信小程序只做壳，用 WebView 打开页面。

优点：

- 改造成本最低。
- 当前 UI 和动画保留最多。
- 适合快速验证玩法和用户反馈。

缺点：

- 小程序原生能力受限。
- 登录、支付、分享、审核体验更复杂。
- 儿童产品和长期运营可能受 WebView 限制。

适合阶段：

- 原型验证。
- 内测。
- 先看玩法是否成立。

### 路线 B：Taro 或 uni-app 迁移

做法：

- 使用跨端框架重建页面和组件。
- 复用一部分 TypeScript 逻辑。
- 将存储、音频、图片、触控等改成框架或小程序 API。

优点：

- 比原生小程序迁移成本低。
- 可以保留部分 React 思维和 TS 逻辑。
- 更接近正式小程序体验。

缺点：

- 当前 Tailwind、motion、DOM API 不能完全直接复用。
- 游戏组件仍需较多适配。
- 动画和音频需要重新验证。

适合阶段：

- 想正式上线，但仍希望控制重写成本。
- 团队愿意接受跨端框架。

### 路线 C：原生微信小程序重写

做法：

- 使用 WXML/WXSS/JS 或 TypeScript 原生小程序结构重建。
- 游戏逻辑可参考当前源码重写。
- 存储、音频、图片、登录、云开发全部使用微信生态 API。

优点：

- 与微信生态贴合最好。
- 性能、审核、原生能力最稳。
- 长期维护边界清晰。

缺点：

- 初期成本最高。
- 当前 React UI 基本不能直接复用。
- 需要重新搭建组件、状态、动画和测试。

适合阶段：

- 已决定长期做正式产品。
- 重视微信原生体验、家长授权、云端数据和可维护性。

## 当前建议

短期建议：

1. 先决定小程序路线：WebView、Taro/uni-app、原生小程序。
2. 结合 `数据模型草案.md` 明确云端数据边界。
3. 用 Web 版继续做四个游戏逐项交互测试和玩法调整。

中期建议：

- 如果目标是快速上线试水，考虑 WebView。
- 如果目标是正式小程序 MVP，优先评估 Taro/uni-app。
- 如果目标是长期儿童产品，最终更建议原生小程序或非常克制的跨端方案。

## 迁移前必须处理的问题

- 积分重复发放已修复，但仍需逐项手动验证四个游戏结算体验。
- 本地假排行榜。
- `localStorage` 数据模型。
- 音效播放方案。
- 图片上传和头像裁剪。
- 儿童隐私、家长授权和数据合规。

## Web API 替换表

| 当前 Web API | 小程序方向 |
| --- | --- |
| `localStorage` | `wx.getStorageSync` / `wx.setStorageSync` / 云数据库 |
| `window` | 页面生命周期或框架 API |
| `document` | 小程序组件、SelectorQuery、Canvas API |
| `new Image()` | `wx.getImageInfo`、Canvas 或文件 API |
| `URL.createObjectURL` | 小程序临时文件路径 |
| `AudioContext` | `wx.createInnerAudioContext` 或静音降级 |
| React DOM | Taro/uni-app/原生小程序页面 |

## 云端数据初步方向

如果正式上线，至少需要：

- 用户档案
- 积分流水
- 游戏记录
- 成就状态
- 每日打卡记录
- 排行榜快照或排行榜查询

详细数据模型已记录在 `数据模型草案.md`，确定路线后再转成具体集合和云函数/API 设计。
